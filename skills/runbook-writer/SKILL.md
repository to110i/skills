# Runbook Writer

コマンド操作を伴う運用手順書を作るためのskill。

手順書の読者は、**作業当日に緊張しながら、上から順にコマンドをコピー&ペーストしていく人**だと考えてほしい。その人は書いた本人ではないことが多く、深夜のメンテナンス時間帯かもしれないし、障害の最中かもしれない。だから良い手順書とは「読んだ人が迷わず、判断が必要な場面ではその判断材料が書いてあり、失敗しても安全に戻れる」文書のこと。以下の指示はすべてここから来ている。

## ワークフロー

### 1. 作業内容を把握する

手順書を書き始める前に、次の点を把握する。会話の文脈、リポジトリ内のファイル、ユーザーの説明から分かることは自分で埋め、**分からず、かつ手順に大きく影響するものだけ**ユーザーに質問する（質問は一度にまとめる）。

- **目的**：何のための作業か、完了したら何がどうなっているべきか
- **対象環境**：本番 / ステージング / 検証、ホスト名・クラスタ・アカウント・リージョン・DBなど
- **影響範囲**：サービス停止の有無、ユーザー影響、関連システム
- **前提**：必要な権限、ツールとそのバージョン、作業端末（踏み台経由かなど）
- **作業時間帯・所要時間の目安**

リポジトリ内に関連するもの（`Makefile`、`scripts/`、Terraform、k8sマニフェスト、Ansible、CI設定、既存の手順書）があれば先に読む。実際のリソース名・スクリプト名・既存の慣習に合わせたコマンドを書けるので、一般論の手順書よりはるかに役立つ。既存の手順書があれば、その書式・保存場所に合わせる。

情報が足りないまま進める場合は、仮定した値を手順書冒頭の変数定義にまとめ、「要確認」と明記する。黙って推測で埋めないこと。

### 2. コマンドを安全な範囲で検証する

手順書に載せるコマンドが正しいか、**副作用のない方法で**確かめる。存在しないオプションや古い構文が手順書に残ると、作業当日に作業者が立ち往生するので、確かめられるものは確かめる。

実行してよいもの（読み取り専用・副作用なし）：
- `--help`、`man`、`--version` でのオプション・構文確認
- 参照系：`kubectl get/describe`、`aws ... describe-*/list-*/get-*`、`systemctl status`、`df`、`ls`、`cat`、`SELECT`（ロックを取らない小さなクエリ）など
- dry-run：`terraform plan`、`kubectl apply --dry-run=client`、`ansible --check`、`rsync -n` など

実行しないもの：
- 状態を変えるコマンド全般（作成・更新・削除・再起動・デプロイ・`apply`・`INSERT/UPDATE/DELETE`・DDLなど）
- 本番環境に対するもの全般（参照系でも、接続先が本番と分かったらユーザーに確認してから）
- 認証情報を出力・送信するもの

そもそも実行環境がない場合（対象サーバーにアクセスできないなど）は、無理に検証しなくてよい。その代わり、確認できなかったコマンドには手順書内で `⚠️未検証` の印を付け、最後のレポートでユーザーに伝える。手順書はGitLab等でレンダリングして読まれるので、`<!-- -->` のようなHTMLコメントは画面に出ず、印として機能しない。何を検証済みで何が未検証かを正直に区別することが、手順書の信頼性そのもの。

### 3. 手順書を書く

`references/template.md` のテンプレートを読んで、その構成に沿って書く。作業の規模に応じて節は省略・統合してよい（5分で終わる参照系の作業に重厚な承認欄はいらない）。ただし **前提条件・事前確認、各手順の期待結果、ロールバック手順** の3つは必ず含める。この3つが欠けた手順書は、作業者を危険にさらすから。

#### 書き方の原則

**短く、表で、見て分かるように。**
作業者は手順書を「読む」のではなく、画面の出力と「見比べる」。文章が多いと、必要な1行（コマンドと期待結果）が埋もれる。
- 1行のコマンドで期待結果も1行で言える確認（事前確認・事後確認の大半）は、`| 確認内容 | コマンド | 期待結果 |` の表にまとめる。1つずつ見出しとコードブロックを立てない
- 表のセルに入れるコマンドは、短くてパイプ（`|`）を含まないものだけにする。セル内の `|` は `\|` とエスケープが必要で、生のMarkdownからコピーすると壊れる。長いコマンドやパイプを含むコマンドは、セルに「下記」と書いて表の下にコードブロックで置く
- 見出し付きの手順にするのは、複数行のコマンドや状態を変える操作だけ
- 期待結果は `→ **期待結果**：…` の1行で書く。出力例は、作業者が値を見比べる必要があるときだけ、必要な行だけ載せる
- 「期待と違う場合」の対応が1つだけ（例：中断してロールバック）なら、表にせず `→ 違う場合：中断して R1 へ` の1行で書く。症状ごとに対応が分かれるときだけ `| 症状 | 対応 |` の表にする
- 同じ手順を複数台・複数環境に繰り返す場合、手順は1回分だけ書き、対象は「web01 → web02 の順に1台ずつ」と冒頭で示す（ホストごとに値が違うなら変数の表にする）
- 「なぜそうするか」の説明は、作業者の判断に必要なものだけ1文で。背景や詳しい理由は末尾の備考へ
- 手順の冒頭に「手順 / 作業 / 実行場所 / 戻せるか」の一覧表を置くと、全体像と戻れない地点が一目で分かる
- 短くするために安全のための確認を削らない。削るのは言葉であって、確認ではない（LBからの切り離し、操作するアカウント・クラスタ・DBの確認、ロック待ちの確認などは残す）

#### 文章の書き方

手順書の文章は、作業中に一瞬で目に入る必要がある。次のルールで書く。

- **改行を細かく入れる。** 1段落に2文以上つなげない。話題が変わったら改行する。Markdownでは空行を挟まない改行は1行につながって表示されるので、段落の間には空行を入れる
- **箇条書きは、並べる項目があるときに使う。** 条件・確認項目・選択肢などの並列な情報は箇条書きにする。ただし、ひとつながりの文章を細切れにしただけの箇条書きにはしない
- **一文に情報を詰め込まない。** 1文に伝えることは1つ。条件と操作と理由を1文に入れたくなったら、文を分ける
- **短い言葉で済むなら短い言葉を使う。** 「〜を実施する」→「〜する」、「〜することが可能」→「〜できる」、「〜を行う」→「〜する」
- **削れる言葉は削る。** 「必ず」「しっかり」「念のため」などの修飾語や、比喩は使わない。削っても意味が変わらない言葉は削る
- **能動態で書く。** 作業者の操作は「〜を削除する」「〜を再起動する」と書き、「〜が削除される」「〜が実行される」としない。誰が何をするかがはっきりする。期待結果の「〜と表示される」のように、画面の状態を表す受動態は使ってよい

例：

- 悪い：`この手順では、念のため現行の証明書ファイルを事前にバックアップしておくことで、万が一問題が発生した場合にも迅速に切り戻しを行うことが可能となります。`
- 良い：`現行の証明書をバックアップする。R1 の切り戻しで使う。`

**コマンドはそのままコピペで動く形にする。**
- 環境ごとに変わる値は冒頭で変数として定義し（`export TARGET_HOST=...`）、本文では `"$TARGET_HOST"` として参照する。本文中に `<ホスト名>` のようなプレースホルダーを散らすと、置き換え漏れが起きる
- 1つのコードブロックには、1回で貼り付けて実行するひとまとまりだけを入れる。出力例とコマンドは別のブロックに分ける
- プロンプト記号（`$`、`#`）はコマンドに付けない
- クォートが入れ子になる長いワンライナー（`ssh host "sudo sh -c '...'"` など）は貼り付けで壊れやすい。対象ホストにログインしてから実行する形に分けるなど、単純にする
- どのホスト・どのユーザーで実行するかが手順の途中で変わるなら、そこで明示する

**期待結果と、期待と違ったときの行動を必ず書く。**
期待結果は「成功しました」ではなく、作業者が画面と見比べられる具体的なもの（ステータス値、件数、HTTPステータスなど）にする。作業者が一番困るのは、想定外の出力を前に「続けていいのか」が分からないとき。

**危険な操作は目立たせる。**
状態を変える手順、特に元に戻せない手順（データ削除、DROP、上書き）には `> ⚠️` の1〜2行の引用ブロックを付ける。対象環境の取り違えは典型的な事故なので、危険な操作の直前には接続先の確認（`kubectl config current-context`、`hostname`、`SELECT current_database();` など）を入れる。

**ロールバックは「いつ戻すか」と「どう戻すか」の両方を書く。**
判断基準、進捗ごとの戻し方の表、戻せない地点の明示、戻した後の確認方法。ロールバック手順そのものは、作業者がそのまま実行できる形にする（「参考SQL。そのまま実行しないこと」は、本番で役に立たない）。

**再実行の安全性に触れる。**
途中で中断した作業を再開するのはよくあること。2回実行して危険な手順にだけ、再実行前の確認方法を書く。

### 4. 保存する

- リポジトリに既存の手順書置き場があればそこに合わせる。なければ `docs/runbooks/` に保存する
- ファイル名は内容が分かる英小文字ハイフン区切り（例：`rotate-tls-certificate.md`、`monthly-db-vacuum.md`）
- ユーザーが保存場所を指定していればそれに従う

### 5. 見直して報告する

保存前に、作業者になったつもりで頭から読み直す。

- 変数はすべて冒頭で定義されているか、本文に未定義の変数やプレースホルダーが残っていないか
- 各手順に期待結果があるか、それが具体的か
- 危険な操作の前に接続先の確認があるか
- 途中のどの手順で失敗しても、どう戻せばよいか分かるか
- 手順の番号と、ロールバック節から参照している番号がずれていないか
- 表にできるのに文章や個別の見出しになっている箇所、作業者の判断に関係しない説明が残っていないか
- 「文章の書き方」のルールに沿っているか（長い一文、削れる言葉、操作の受動態がないか）
- テンプレートの `{{ }}` が残っていないか（未確定の値は「要確認」と書く）

最後にユーザーへ短く報告する：保存場所、手順書の概要（数行）、検証済みのコマンドと未検証のコマンド、仮定した値や要確認事項。
